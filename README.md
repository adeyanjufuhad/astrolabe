# Astrolabe

**Find UI values that drifted away from your design system before they ship.**

Astrolabe opens your pages in a real browser, reads the styles that actually render, and checks every color, spacing value, radius, font size, font family and font weight against your design tokens. For each value that isn't a token, it tells you the closest one.

```
$ astrolabe check https://staging.shop.com/checkout --tokens tokens.json

Astrolabe  https://staging.shop.com/checkout
Fidelity 94%  ·  189 of 201 values on-token  ·  7 off-token values

  near-miss   color        #3b82f7  ×1  → color.blue.500 (#3b82f6) ΔE 0.1   button.pay-button
  near-miss   spacing      13px     ×1  → space.3 (12px) 1px off            aside.order-summary
  near-miss   font-size    15px     ×1  → font.size.base (16px) 1px off     p.promo-note
  near-miss   font-weight  700      ×2  → font.weight.semibold (600)        h2.line +1
  off-system  font-family  arial    ×1  → font.family.sans (inter)          button.pay-button
  off-system  color        #ea580c  ×1  → color.gray.500 (#6b7280) ΔE 23.2  p.promo-note
```

Nobody can see that `#3b82f7` is one step off the brand blue. Astrolabe can.

- **Near-miss** means almost a token, probably a typo or a hand-typed value.
- **Off-system** means there's no close token. It's either a deliberate one-off or a gap in your design system.

## Why

Design tokens only help if the shipped UI uses them. Values get hard-coded under deadline pressure, copied from old screens, or generated by AI coding tools that don't know your system. Screenshot-diff tools catch visual changes against a baseline. Astrolabe checks against your **source of truth** instead, so it catches drift on day one, with no baseline needed.

## Install

Download a prebuilt binary for Linux, macOS or Windows (amd64 and arm64) from the [latest release](https://github.com/adeyanjufuhad/astrolabe/releases/latest), unpack it, and put `astrolabe` on your `PATH`. Each release includes a `checksums.txt` to verify the download.

Or build it with Go 1.24 or newer:

```bash
go install github.com/adeyanjufuhad/astrolabe/cmd/astrolabe@latest
```

Astrolabe uses a Chromium-based browser that's already on your machine (Chrome, Edge, Chromium or Brave), so there's nothing else to download. Edge ships with Windows. To use a specific browser, pass `--chrome /path/to/browser` or set `ASTROLABE_CHROME`.

## Quick start

```bash
# Try it on the demo page in this repo
astrolabe check examples/checkout/index.html --tokens examples/checkout/tokens.json --html report.html

# Your local dev server
astrolabe check localhost:3000 localhost:3000/pricing --tokens tokens.json

# In CI: fail the build below 95% fidelity
astrolabe check https://preview.example.com --fail-under 95 --json report.json
```

## Token files

Astrolabe reads the common formats and resolves aliases like `{color.blue.500}`:

```jsonc
// W3C Design Tokens (DTCG)
{ "color": { "$type": "color", "primary": { "$value": "#3b82f6" } },
  "space": { "$type": "dimension", "3": { "$value": "12px" } } }

// Tokens Studio / Style Dictionary
{ "color": { "primary": { "type": "color", "value": "#3b82f6" } } }

// Plain nested JSON
{ "colors": { "primary": "#3b82f6" }, "spacing": { "sm": "4px" }, "rounded": { "lg": "0.5rem" } }
```

Run `astrolabe tokens tokens.json` to see how each token was understood. Colors can be hex, `rgb()`, `hsl()`, `oklch()` or `oklab()`, so Tailwind v4 palettes work. Lengths can be `px`, `rem` or numbers.

## GitHub Action

```yaml
# .github/workflows/design-drift.yml
on:
  pull_request:
  push:
    branches: [main] # scans of main become the baseline for pull requests
permissions:
  contents: read
  pull-requests: write
  actions: read # lets the Action download main's report
jobs:
  astrolabe:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      # ...start your app or wait for a preview deployment...
      - uses: adeyanjufuhad/astrolabe@main
        with:
          urls: |
            http://localhost:3000
            http://localhost:3000/checkout
          tokens: tokens.json
          fail-on-new: true # block only drift this PR adds
```

The Action posts one summary comment on the PR and updates it on every push. It also uploads the HTML and JSON reports as a build artifact and exposes the score as `steps.<id>.outputs.score`.

### Only the drift a pull request adds

On a real codebase, the first scan usually finds plenty of drift that's been there for years. Flagging all of it on every PR turns the comment into noise. So when the workflow also runs on pushes to `main`, each PR is compared with `main`'s latest report (`baseline: auto`, the default):

- The comment leads with what **this change** introduces: new off-token values, and existing ones now used on more elements.
- Values the PR removed are listed as **fixed**.
- Drift that was already on `main` is folded into a collapsed section.
- `fail-on-new: true` fails the job only when the PR adds drift, so you can adopt Astrolabe without fixing the backlog first. `fail-under` still works alongside it.

Until `main` has a report (for example, on the first PR), the Action lists everything and says so. Use `baseline: path/to/report.json` to compare with a specific report, or `baseline: none` to turn comparison off.

The same works locally:

```bash
astrolabe check localhost:3000 --json before.json   # on main
astrolabe check localhost:3000 --baseline before.json --fail-on-new   # on your branch
```

Pages are matched by URL path, so scans of two different preview deployments still line up.

## CLI reference

| Flag | Default | |
|---|---|---|
| `--tokens` | `tokens.json` | Token file |
| `--format` | `text` | stdout format: `text`, `json`, `markdown`, `html` |
| `--json`, `--html`, `--markdown` | | Also write that format to a file |
| `--fail-under` | `0` | Exit 1 when fidelity is below this percentage |
| `--baseline` | | Earlier JSON report to compare with: findings are marked new, increased, existing or fixed |
| `--fail-on-new` | `false` | Exit 1 if a value is new or used more than in `--baseline` |
| `--ignore` | | Comma-separated selectors to skip, e.g. `.ads,#cookie-banner` |
| `--viewport` | `1280x800` | Viewport size |
| `--wait` | `500ms` | Extra wait after load (for client-rendered content) |
| `--px-tolerance` | `0.5` | Lengths within this many px count as a match |
| `--color-tolerance` | `0` | Colors within this OKLab ΔE count as a match (0 = exact) |
| `--chrome` | auto | Browser binary |
| `--upload`, `--project`, `--api-key` | | Send the scan to a history server |

Exit codes are `0` for OK, `1` for below `--fail-under` or new drift with `--fail-on-new`, and `2` for errors.

## History server (optional)

`astrolabe-server` stores scans in Postgres so you can track fidelity over time. It works well on [Neon](https://neon.tech)'s free tier.

```bash
cp .env.example .env   # add your Neon connection string and an API key
go run ./cmd/astrolabe-server
astrolabe check https://example.com --upload http://localhost:8080 --api-key $ASTROLABE_API_KEY
```

| Endpoint | |
|---|---|
| `POST /api/scans?project=NAME` | Store a report (Bearer API key) |
| `GET /api/projects` | Projects with their latest score |
| `GET /api/projects/{name}/scans` | Score history (encode `/` as `%2F`) |
| `GET /api/scans/{id}` | One stored scan |

## How it works

1. Launches your installed Chrome/Edge headless and drives it over the DevTools protocol, through a tiny built-in client with no dependencies.
2. Loads each page, waits for fonts, and reads `getComputedStyle` for every visible element. It skips hidden elements, `margin: auto`, transparent colors and borders that aren't drawn.
3. Compares each value with your tokens. Colors are compared in the perceptual OKLab space, and lengths are compared in px.
4. Groups identical off-token values and ranks near-misses first.

## Limitations

- It checks style **values**, not layout or structure. A button in the wrong place won't be flagged.
- It's only as good as your token file. Values you intentionally keep outside the system will show up as off-system, so use `--ignore` for those areas.
- `rem` tokens assume a 16px root font size.
- It audits one viewport per run. Run it again with `--viewport 390x844` for mobile.
